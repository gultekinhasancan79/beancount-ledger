# reviews/

Recorded review and rollout artifacts. Nothing here is regenerated by the test
suite; each file is a dated record of one run.

The one exception is the deterministic environment witness, which runs in the
standard battery and writes nothing here:
`tests/liveness_witness.py` drives a scripted conforming agent
(`list_files → read_file(ledger) → write_ledger(golden) → submit`) through the
real `evaluate` door on the six panel selectors — `--sentinels` adds the pinned
structural sentinel set — asserting reward 1.0, the TERMINAL phase, artifact
digests bound from the rollout's own `delivery.json`, and turns/output tokens/
observation bytes/write payload inside the package's own declared constants,
identically across two runs. It makes no provider call. A stochastic model
rollout cannot answer the liveness question: a run of zeros is equally
consistent with a broken episode contract and with models that cannot do
bookkeeping (Codex T49 §13.6).

- **`confirmatory_design.md`** — the PRE-REGISTRATION of the `confirm1v4` replay-arm
  experiment, written before any confirmatory cell ran: the fixed-panel estimand,
  the roster and panel, the two delivery estimands, the paired contrasts and

- **`schedule_confirm1v4.json`** — the SEALED (v2) schedule that document
  registers, written by `tests/schedule_arms.py --seal` on the checkout that
  executes it, with the EXECUTION PATHS clean. 144 cells. Beyond the v1 fields
  (provider, model, selector, replicate, arm, planned ordinal, arm position,
  permutation, block — all fixed BEFORE any rollout), a v2 `schedule_id` hashes
  an **experiment contract**: the instrument commit, the closed execution-path
  set, the exclusion list, the on-disk execution-tree digest and its file count,
  the **runtime-environment digest** with its file/byte/distribution counts and
  the interpreter's version string, this document's sha256, the literal
  `ARM_PRESETS` treatment behind each arm label, the expected episode and
  per-arm replay contract digests, the package lock, the failure-map digest
  (bucket rules + the classifier algorithm version + the free-text fallback's
  needles + the provider quota table with its admission semantics + the
  window-rule constants), the active manifest rotation and content digest, and
  each selector's expected public task id. `schedule_id` therefore names the
  treatment, the world, the code, the INTERPRETER and the analysis plan rather
  than merely the order in which three mutable labels are invoked (Codex T49 §2,
  T50 §1–§4, T51 §1–§4).
  `tests/run_arms.py --schedule` re-checks every one of those fields through
  `tests/startup_witness.py` before the first provider call of every session,
  refuses a file that no longer hashes to its own id, refuses `--force`, refuses
  `--no-probe-capabilities`, takes ONE schedule-level executor lock (no
  automatic stale takeover, and an ATOMIC one when `--take-over-lock` is given),
  and executes only whole three-arm blocks.
  **Record the printed `schedule_id` here when it is sealed.**

  **The `.venv` and the interpreter are sealed AS BYTES** (Codex T51 §1). The
  execution-tree walk stops at `.venv/**`, and the replacement binding used to
  be version STRINGS: an in-place edit to `.venv/Lib/site-packages/openai/…`
  changes request construction, retries or token accounting while `METADATA`
  still reports the sealed version. So the seal also walks every directory the
  RUNNING interpreter can import from (`sysconfig`/`sys.prefix`, never a
  repository-relative `.venv` — a builder worktree has none) and hashes: every
  file under the site-package roots AND the STANDARD LIBRARY (hashing
  `python312.dll` does not cover `json/encoder.py` or `ssl.py`); every installed
  distribution's `RECORD`, with its declared sha256 verified against the bytes
  on disk and every mismatch or missing file recorded IN the material; every
  file no RECORD references (the shadow analogue); and the interpreter itself —
  `sys.executable` plus the `pythonXY` runtime library — beside `sys.version`.

  **Identity version 2 seals the IMPORT ENVIRONMENT too**, after an adversarial
  review found three ways past version 1. `PYTHONPATH` was not in the walk at
  all: a directory named there is prepended to `sys.path` and shadows any sealed
  module while the digest stays identical, and every cell inherited `os.environ`
  whole (C1). An existing `.pyc` edited in place keeps its recorded source mtime
  and size, so timestamp validation accepts a tampered body forever and the
  sealed `.py` is never read (C2). And `base_prefix/DLLs` (37 `.pyd` extension
  modules), the `pythonXY.zip` slot, `pyvenv.cfg` and the unreferenced half of
  `Scripts/` were outside the roots (C3). Now: the roots come from `sys.path`
  itself; every `sys.path` entry is classified and the ones nothing seals are
  reported as an explicit list (`[]` here) that the witness refuses on and the
  sealer refuses to seal; the executor strips `PYTHONPATH`/`PYTHONHOME`/
  `PYTHONSTARTUP` from every confirmatory cell and journals it
  (`cell_environment_sealed`); and `PYTHONPYCACHEPREFIX` points at a FRESH
  per-session directory for the executor and every cell, so no pre-existing
  `__pycache__` is reachable and the `.pyc` exclusion becomes sound rather than
  a hole. Measured here on 2026-08-31 at version 2: 19,178 files, 432,376,226
  bytes, 112 distributions, 1,211 stdlib files, 2 files referenced by no RECORD,
  0 uncovered `sys.path` entries; ≈3–5 s with the environment fully cached,
  15–25 s partly evicted, ≈460 s on a first cold read. The remaining perimeter
  — the checkers verify themselves in-process, and no external immutable image,
  read-only mount or content-addressed environment exists on this machine — is
  **accepted as final** and stated in `confirmatory_design.md` §3.1c, with the
  threat model it belongs to: tamper-evidence and provenance, not a defence
  against a privileged local attacker.

  **Both digests are re-verified per CELL and the tree per REQUEST** (Codex T51
  §2), inside the cell subprocess that actually spends the call: a mismatch
  makes no provider call, writes no row, exits 6, is journalled
  `execution_integrity / instrument_drift` fail-closed and STOPS the session.
  The digests are part of EXACT row admission, so a row from a foreign — or
  unidentified — instrument enters no estimand and makes `arm_table` exit 4.

  **The identity rule is the BYTES ON DISK, not commit equality and not git's
  index** (Codex T50 §1, hardened by the adversarial review of that fix). The
  sealed schedule is itself a file in this repository, so committing it moves
  HEAD; a witness demanding `HEAD == instrument_commit` could never pass for the
  run it was sealed for, and Turn 50 found exactly that. But asking git instead
  is no better: `--assume-unchanged` plus an edit, a shadowing module beside the
  package (`sys.path[0]` for every cell process), and a file hidden by a
  `.gitignore` line committed on an EVIDENCE path all left an all-git witness
  fully green. So the PRIMARY check walks `environments/beancount_ledger/` on
  disk — skipping `reviews/**` (evidence), `.venv/**` (bound instead by
  `package_lock` and the replay-contract digests), `**/__pycache__/**` and
  `*.pyc` — hashes every remaining file's ACTUAL BYTES, and digests the sorted
  `(relative path, sha256)` pairs together with the root and the exclusion list,
  so an ADDED or REMOVED file moves it too. The file count is sealed beside the
  digest. The git checks (ancestry, an empty `git diff <instrument>..HEAD` over
  those paths, a clean working tree over them) are kept as SECONDARY evidence. A
  dirty or newly committed EVIDENCE file — anything in `reviews/`,
  `design_chat/` or a root `*.md` — does not refuse the run. The RUNTIME head
  and execution-tree digest are recorded separately on every row and every
  journal entry, and the table prints both identities side by side.

- **`schedule_<label>.json.window.jsonl`** — the shared PROVIDER-WINDOW LEDGER
  for a schedule (Codex T49 §6): one appended line per HTTP attempt, carrying
  epoch and monotonic timestamps, the model, the cell tag, the status and the
  estimated/billed tokens. Two things depend on it and neither can be answered
  inside one cell's process: the 6-second pacing interval is enforced against
  ITS last entry for the provider (each cell is a fresh subprocess, so the
  process's own memory is empty at exactly the boundary that matters), and a 429
  archives the observed trailing-60-second window it was refused in, split into
  this cell's own contribution and the carry-over from the cell before. It
  carries no prompt content and no secret.

  Since Codex T50 §5 the ledger also **fails loud on damaged evidence**: any
  malformed or non-dict line, and any file that ends mid-record (a killed
  process), makes it UNHEALTHY, and an unhealthy ledger refuses the next
  provider request rather than being read past line by line. The bytes are
  never repaired or deleted. Recovery is an explicit operator act,
  `tests/run_arms.py --recover-window-ledger`, which appends a
  `window_ledger_recovery` segment boundary acknowledging the damaged lines,
  is journalled fail-closed, and makes every rate-limit classification whose
  window spans the boundary `ambiguous`.
- **`schedule_<label>.json.exclusions.jsonl`** — the immutable,
  content-bound CONFIGURATION-EXCLUSION records (Codex T50 §8): one per
  (provider, model) whose capability probe conclusively failed or which was
  stopped mid-run. Each carries the schedule id, the reason, the session, the
  sealed instrument commit, the runtime HEAD and a `record_digest` over its own
  content. `tests/arm_table.py` consumes them to exclude a whole configuration
  even when the cells they block have no rows at all — the resumed-run case
  row-level classification cannot see — and refuses (exit 2) a record whose
  digest does not recompute.
- **`arms_<label>_execution.jsonl`** — the executor's append-only journal:
  capability-probe results, execution-integrity quarantines, and every cell's
  start, finish, session id and actual ordinal — including cells whose
  subprocess crashed without writing a row, which the actual-order census would
  otherwise never see. Since Codex T50 §6 it **fails CLOSED in confirmatory
  mode**: the append is locked, flushed and fsync'd, its success is checked, and
  a failure aborts the action the entry authorizes (`run_arms.py` exits 5). The
  startup witness runs a create/append/read-back probe on it before request 1,
  and every entry carries the runtime HEAD, the execution-tree digest and the
  runtime-environment digest. Probe outcomes have four distinct
  event types — `probe_passed`, `capability_failed`, `probe_inconclusive`,
  `inconclusive_accepted` — because an inconclusive probe establishes nothing
  and must never be recorded as an incompatibility (§7).

  Since Codex T51 §4 it also fails closed on **corruption**, in every mode: the
  WHOLE file is parsed under the append lock before every append and before the
  probe, and any malformed or non-object line — a crash's truncated tail, or the
  malformed middle the old probe manufactured by appending after one — aborts
  the action the entry authorizes. The bytes are never repaired or deleted.
  Recovery follows the window ledger's shape and Codex's own Q4 policy:
  **before the first real row exists there is no recovery path** —
  `--recover-execution-journal` refuses and says abort and reseal — and after a
  cell has a real row it appends an immutable `execution_journal_recovery`
  segment boundary with a provenance record (segment, acknowledged lines,
  reason, session, operator, runtime identity). `arm_table` refuses the
  confirmatory estimands (exit 4) while a malformed line stands unacknowledged;
  an acknowledged boundary is CLEAN WITH A NOTE and is rendered as such.
- **`schedule_<label>.json.lock`, `.lock.takeover`, `.lock.displaced.<session>.json`**
  — the schedule-level executor lock (session id, nonce, pid, host, start), the
  `O_EXCL` guard that makes `--take-over-lock` an atomic competition, and the
  exact preserved bytes of a lock a takeover displaced (Codex T51 §3). Exactly
  one contender may take a stale lock over; a lock younger than five minutes is
  a live executor and is refused; after acquisition the executor re-reads the
  lock and proves the nonce is its own before anything runs.

- **The 2026-08-30 arm set (tags `Ap_*`, `B1p_*`, `B2p_*`, `tests/run_arms.py`)**
  is the CORRECTED diagnostic set — the first (and, as of this writing,
  only) run under the corrected episode contract (2 cells completed, then
  stopped) — and is a **hidden-output-budget, unpinned-sampling
  DIAGNOSTIC** (Codex T47 §8/§11, Q12) — it answers "did the corrected
  machinery run, deliver artifacts and record the intended fields", never
  "which arm wins". Three concrete reasons it cannot be read as an
  arm-effect estimate:
    1. temperature/top_p/seed were not pinned or recorded on these rows
       (`tests/seed_probe.py` additionally found, live, that this endpoint
       does NOT honour `seed` for `nemotron-3-nano-30b-a3b` — three
       `seed=1234, temperature=0` calls were not byte-identical — so even a
       later re-run WITH a seed pinned is not guaranteed reproducible on
       this model family without re-probing);
    2. one rollout per (selector, model, arm) cell cannot support a stable
       median/p75, and Q10's economic threshold needs both conditional cost
       AND effective cost per correct delivery (`tests/arm_table.py`),
       neither of which is estimable from n=1;
    3. `budget_accounting` did not exist yet on the measurement side when
       this set ran — this is a WHOLESALE exclusion, not "some rows lack a
       cross-check": EVERY row in this set lacks the field entirely.
       `tests/arm_table.py` derives a best-effort `"VALID/derived"` from
       each row's own `per_turn` (`derive_budget_accounting`) rather than
       reporting n=0 for the whole set, but a derived row can only check
       that per-turn caps and usage are PRESENT — it has no `wire_caps`, no
       `attempts` (framework-retry) signal and no env fail-closed code to
       check further, so it is a strictly weaker guarantee than a row a
       live, current instrument produced. `tests/stamp_contract_digest.py
       --backfill-accounting` can write the SAME derived verdict into the
       archived files, marked `budget_accounting_stamped: true`, so a
       reader of the raw JSON does not have to re-derive it by hand.
  **Never merge this arm set with the confirmatory one.** Since Codex T48 the
  refusal is mechanical rather than a convention: these rows carry no
  `replay_contract_digest`, no attempt identity and no `schedule_id`, so
  `tests/arm_table.py` re-derives them as `VALID/derived` (admissible only
  through `--pilot`) and REFUSES, as an error, to put them in a condition
  beside a `confirm1_` row. Read them with
  `tests/arm_table.py --tag-prefix Ap_ B1p_ B2p_ --label pilot-<date> --pilot`;
  the table labels itself "instrument smoke test" and is not decision-bearing.
- **The `confirm1v4_*` arm set (`tests/run_arms.py --schedule
  reviews/schedule_confirm1v4.json`)** is the decision-bearing one, read with
  `tests/arm_table.py --label confirm1v4 --schedule
  reviews/schedule_confirm1v4.json`. In confirmatory mode the table needs no
  `--tag-prefix`: it derives the exact 144 expected file paths from the
  schedule, refuses duplicate rows for one cell and refuses any file carrying
  the schedule's label that is not one of them (Codex T49 §3). There is no
  `--schedule-complete` either — completion is DERIVED from that exact cell map,
  because an operator who can declare a run finished after seeing the results is
  choosing the denominator with the outcome in view. Its pre-registration is
  `confirmatory_design.md`; its estimand is the average arm contrast over the
  fixed panel of four Mistral models × six selectors, and nothing in it
  generalises past that panel. Cost is reported as MEASURED, never adjudicated:
  no practicality threshold is declared for this run, so no figure it produces
  may be called practical, acceptable or affordable. The exact sentence M2 may
  close with is quoted verbatim in `confirmatory_design.md` §11, together with
  the six things that must be green before it is written.
  The table closes with an **execution-evidence section** (Codex T50 §9) — the
  runtime HEAD and verified tree identity of every row, the probe outcome per
  configuration with inconclusive distinguished from incompatible, journal
  health with any takeover or ledger-recovery event, the per-429 billed /
  rejected-estimate / current-request evidence with the TPM and RPM verdicts
  separately and the conservative combined bucket, the ledger gap and health
  status, and both censuses. It is audit evidence for the pre-registered
  estimands: it introduces no outcome metric and no decision threshold.
